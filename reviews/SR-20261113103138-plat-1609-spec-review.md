## Summary

Ticket: PLAT-1609. Spec review of the FR-037 amendment, which adds "A JSON report has no source commit; its requests set `SOURCE_DATE_EPOCH` to `0`" and amends FR-037-AC-1 to match. Sub-analyses chosen by scope: EARS/normative wording, and consistency with the rest of FR-037 and NFR-011. `quire validate` on FR-037 passes.

Is `0` the right value? It is defensible. A JSON report is generated, not committed, so it has no commit date to use. Every converter needs some fixed value, and pandoc's DOCX writer always writes `docProps/core.xml` from `getTimestamp`, which reads `SOURCE_DATE_EPOCH` because the writer is not sandboxed. With `0`, core.xml reads 1970-01-01T00:00:00Z. zip-archive's `epochTimeToMSDOSDateTime` clamps zip entry times below 1980 to 1980-01-01, so the zip neither fails nor wraps. Typst accepts `0` and writes D:19700101000000Z. The value is stable, which is all NFR-011 needs. JSON reports are outside NFR-011's Scope anyway, and an epoch date is a recognisable "no date" sentinel. One alternative needs no spec change: typst's `set document(date: none)` would omit the PDF date. Pandoc cannot omit the DOCX dates.

## Verdict

Changes requested, one medium. The choice of `0` is sound and stable. The amendment needs to carry the same exception into the Description and the document-properties bullet so that FR-037 does not contradict itself. NFR-011 does not need to change for JSON reports, which are outside its Scope.
